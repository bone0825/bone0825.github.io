특정 Agent에 접근할 수 있는 사람의 명단이 **뷰의 `WHERE` 조건에 하드코딩**되어 있었습니다.

```sql
-- 대략 이런 형태
CREATE VIEW V_MEMBERS AS
SELECT * FROM V_USERS
WHERE DEPT_PROJECT IN ('...', '...', '...')
   OR DEPT_DIVISION IN ('...', '...')
   OR DISPLAY_NAME LIKE '...%'
   OR LAST_NAME IN ('...', '...');
```

동작은 합니다. 문제는 **바뀔 때마다 사람이 SQL을 고쳐야 한다**는 것입니다.
인사이동, 신규 입사, 조직 개편 — 그때마다 뷰를 수정하고 재배포합니다.
누가 왜 이 명단에 있는지도 SQL을 읽어야 알 수 있습니다.

이걸 테이블 기반으로 바꿨습니다.

## 명단을 옮기지 않고 규칙을 옮겼다

가장 단순한 전환은 **사람 이름을 그대로 테이블에 넣는 것**입니다.
대상이 80명이면 80행이 됩니다.

그렇게 하지 않았습니다. 원래 `WHERE` 조건이 이미 **규칙**이었기 때문입니다.
"이 본부 소속 전원", "이 팀 전원", "그리고 개별로 몇 명" 같은 형태였습니다.

그래서 **규칙을 그대로 행으로 옮겼습니다.**

| | 명단을 옮기면 | 규칙을 옮기면 |
|---|---|---|
| 행 수 | 대상 인원만큼 (수십 행) | **18행** |
| 신규 입사자 | 행 추가 필요 | **자동 포함** (조직 매칭) |
| 조직 개편 | 전수 재작성 | 해당 행만 수정 |

18행이 80명 가까이로 전개됩니다.
조직 단위 매칭이 11행, 개별 지정이 7행이었습니다.

## 매칭 설계 — UNIT과 TAG

매핑 테이블은 이렇게 생겼습니다.

```sql
ROLE_ID   -- 역할명          예: R_TEAM
UNIT      -- 조직/개인 구분   DEPT | USER
TAG       -- 매칭 대상 컬럼   PROJECT | DIVISION | DISPLAY | LASTNAME | ACCOUNT
NAME      -- 매칭 값
```

`UNIT` 2종만으로는 부족했습니다.
조직 정보가 한 컬럼이 아니라 여러 컬럼에 흩어져 있었기 때문입니다.

| UNIT | TAG | 매칭 컬럼 | 방식 |
|---|---|---|---|
| DEPT | PROJECT | 사업/프로젝트 | `=` |
| DEPT | DIVISION | 담당/부문 | `=` |
| DEPT | DISPLAY | 표시명 | **`LIKE`** |
| USER | LASTNAME | 이름 | `=` |
| USER | ACCOUNT | 계정 | `=` |

`DISPLAY` 만 `LIKE` 인 이유는 "○○팀"으로 시작하는 하위 팀을 한 행으로 묶기 위해서입니다.
`UNIT` 2종만 쓰면 대상이 과다 추출되고, **TAG 5종을 쓰니 원래 명단과 정확히 일치**했습니다.

뷰는 하드코딩 조건 대신 이 테이블을 조인합니다.

```sql
CREATE OR REPLACE VIEW V_MEMBERS AS
SELECT DISTINCT u.*
FROM   V_USERS u
JOIN   ROLE_MAPPING m ON m.ROLE_ID = 'R_TEAM'
  AND (
      (m.TAG='PROJECT'  AND u.DEPT_PROJECT  = m.NAME)
   OR (m.TAG='DIVISION' AND u.DEPT_DIVISION = m.NAME)
   OR (m.TAG='DISPLAY'  AND u.DISPLAY_NAME  LIKE m.NAME)
   OR (m.TAG='LASTNAME' AND u.LAST_NAME     = m.NAME)
   OR (m.TAG='ACCOUNT'  AND u.NAME          = m.NAME)
  );
```

이제 **권한 대상이 코드가 아니라 데이터로 결정됩니다.** 행을 추가하면 대상이 늘어납니다.

## 역할 계층 — 명단을 관리하지 않는 쪽으로

역할을 두 개로 나눴습니다.

```sql
CREATE ROLE R_DEFAULT;   -- 누구나 쓰는 기본 Agent
CREATE ROLE R_TEAM;      -- 기본 + 제한 Agent

GRANT ROLE R_DEFAULT TO ROLE R_TEAM;   -- 계층: 상위가 기본을 상속
GRANT ROLE R_DEFAULT TO ROLE PUBLIC;   -- 기본은 전 직원
```

`R_DEFAULT` 를 `PUBLIC` 에 부여한 게 핵심입니다.
**전 직원이 대상이면 명단을 관리하지 않는 게 맞습니다.**
매핑 테이블에는 `R_TEAM` 행만 넣었습니다.

그리고 계층 덕분에 `R_TEAM` 보유자에게 기본 역할을 중복 부여할 필요가 없습니다.

## 여기서 한 번 틀릴 뻔했다 — 뷰는 권한이 아니다

뷰를 다시 만들고 나면 끝난 것 같습니다. 대상이 정확히 나오니까요.

**아닙니다.** 뷰는 "누가 대상인지"를 보여주는 목록일 뿐이고,
실제 접근을 결정하는 건 `GRANT ROLE ... TO USER` 입니다.

```text
ROLE_MAPPING (명단 규칙)
      ↓
   V_MEMBERS (대상 목록)        ← 여기까지는 "누가 대상인가"
      ↓  ⚠️ 자동으로 연결되지 않음
   GRANT ROLE                   ← 여기부터가 "실제로 접근되는가"
      ↓
   앱의 권한 체크
```

Phase 4에서 뷰를 읽어 `GRANT` 문을 생성해 실행했지만, **그건 1회성**입니다.
다음 날 조직이 바뀌면 뷰는 갱신되는데 실제 `GRANT` 는 그대로입니다.
둘이 조용히 어긋나기 시작합니다.

### 그래서 동기화가 필요하다

저장 프로시저와 Task로 매일 정합화하도록 만들었습니다.

```text
① 대상 뷰 조회        V_MEMBERS
② 실제 GRANT 조회     SHOW GRANTS OF ROLE
③ 차집합             ①-② → GRANT / ②-① → REVOKE
④ 보호 목록 제외      PROTECTED_USERS
⑤ 결과 로그          SYNC_LOG
```

Task는 하루 한 번 새벽에 돌립니다. 필요하면 수동으로도 호출합니다.

프로시저에 **`DRY_RUN` 파라미터**를 뒀습니다.

```sql
CALL SP_SYNC_ROLE(TRUE);    -- 미리보기: 무엇을 GRANT/REVOKE 할지만 출력
CALL SP_SYNC_ROLE(FALSE);   -- 실제 적용
```

권한을 회수하는 코드는 **실행 전에 결과를 볼 수 있어야** 합니다.

## 자동 REVOKE의 위험 — 보호 목록

이 설계에서 가장 조심스러운 부분이 `REVOKE` 입니다.

뷰에서 빠지면 자동으로 권한이 회수됩니다. 의도한 동작입니다.
그런데 **매핑 규칙이 잘못 수정되거나 원본 사용자 데이터가 일시적으로 비면,
대상 전원이 뷰에서 사라지고 다음 실행에서 전부 회수됩니다.**

관리자 계정까지 회수되면 복구할 손이 없어집니다.

그래서 자동 회수 제외 목록을 별도 테이블로 뒀습니다.

```sql
INSERT INTO PROTECTED_USERS(ROLE_ID, NAME, NOTE)
VALUES ('R_TEAM', '<관리자 계정>', '<사유>');
```

**자동화에 회수 권한을 줄 때는, 그 자동화가 스스로를 잠글 수 없게 만들어야 합니다.**

## 검증 — 잃는 사람이 없다는 것부터

적용 전에 세 가지를 확인했습니다.

| | 확인 내용 |
|---|---|
| ① | 새 뷰의 멤버 수가 기존 명단과 같은가 |
| ② | **신·구 차집합이 양방향으로 0인가** |
| ③ | 실제 `GRANT` 된 유저 수가 뷰와 같은가 |

②가 핵심이었습니다. 숫자만 같고 구성이 다를 수 있으니까요.

실제로 차집합을 떠보니 **한 명이 어긋나 있었습니다.**
방향이 중요했는데, "대상인데 아직 부여받지 못한" 쪽이었습니다.
즉 적용하면 **권한을 잃는 사람은 0명이고, 못 받던 한 명이 정상화**되는 것이었습니다.

이걸 확인하기 전에는 적용 버튼을 누를 수 없었습니다.
반대 방향이었다면 — 부여받고 있었는데 새 규칙에서 빠지는 사람이 있었다면 —
그 사람이 왜 빠지는지 먼저 설명할 수 있어야 했습니다.

## 컷오버 — 앱은 매핑 테이블을 모른다

마지막 단계는 애플리케이션 전환이었고, 바뀐 건 **상수 한 줄**이었습니다.

```diff
- REQUIRED_ROLE = "TEMP_ROLE"
+ REQUIRED_ROLE = "R_TEAM"
```

앱은 `SHOW GRANTS TO USER` 로 **역할 보유 여부만** 확인합니다.
매핑 테이블을 조회하지 않습니다. 이건 누락이 아니라 설계입니다.

```text
ROLE_MAPPING → 뷰 → 동기화 Task → GRANT → 앱은 GRANT만 확인
```

명단 로직이 앱에 들어가면 규칙이 바뀔 때마다 앱을 재배포해야 합니다.
앱이 아는 것은 "이 사용자가 이 역할을 갖고 있는가" 하나뿐이어야 합니다.

한 줄만 바뀌었으므로 롤백도 되돌리기 한 번입니다.

## 정리

- 명단을 옮기지 말고 **규칙을 옮길 것.** 원래 조건이 규칙이었다면 행 수가 훨씬 줄어든다
- 전 직원이 대상인 권한은 **명단을 관리하지 않는 게 맞다.** `PUBLIC` 에 부여
- **뷰는 권한이 아니다.** 대상 목록과 실제 `GRANT` 는 별개이고, 방치하면 조용히 어긋난다
- 권한을 회수하는 자동화에는 **미리보기 모드와 보호 목록**이 있어야 한다
- 적용 전 검증은 개수가 아니라 **양방향 차집합.** "잃는 사람이 0명"을 먼저 증명할 것
- 앱은 역할 보유만 확인하게 두고, **명단 로직을 앱 밖에 둘 것**

## 남은 것

- 이름 기반 매칭은 **동명이인 위험**이 있습니다. 가급적 계정 단위로 지정하는 편이 안전합니다
- 자동 `REVOKE` 가 발생했을 때 알림이 아직 없습니다. 로그 테이블에는 남지만 아무도 즉시 알지 못합니다. 권한이 조용히 사라지는 건 조용히 유지되는 것보다 나쁩니다
