운영 중이던 AI 서비스의 크레딧 사용량이 급증했습니다.

원인은 명백해 보였습니다. **에이전트 사용량이 늘었으니 LLM 호출이 늘었겠지.**
사용자가 늘어난 시기와 대체로 겹쳤고, 설명이 깔끔했습니다.
그렇게 정리해서 문서까지 썼습니다.

## 그런데 이력이 맞지 않았다

문서를 쓰고 나서 확인차 실제 추론 함수 호출 이력을 조회했습니다.

**크레딧이 폭증한 날에 그 호출이 없었습니다.**

사용량이 늘어난 건 사실이었지만, 그것만으로는 폭증 폭이 설명되지 않았습니다.
제 결론은 반쯤 틀린 것이었습니다. 맞는 요인 하나를 잡고 전체를 설명했다고 착각한 겁니다.

여기서 두 가지를 다시 봐야 했습니다.

- 폭증한 날의 **비용이 어디서 나왔는가** (호출이 아니라면)
- 애초에 **내가 왜 그렇게 확신했는가**

## 진짜 원인 — 뷰 정의 안에 LLM이 있었다

비용 발생 지점을 거슬러 올라가니 특정 뷰가 나왔습니다.
그 뷰의 정의를 열어보고 나서야 이해했습니다.

```sql
-- 대략 이런 형태였습니다
CREATE VIEW ANALYSIS_V AS
SELECT
    id,
    raw_text,
    SNOWFLAKE.CORTEX.COMPLETE('...', raw_text) AS summary  -- ← 여기
FROM SOURCE_TABLE;
```

뷰는 **저장된 쿼리**입니다. 데이터를 들고 있지 않습니다.
따라서 이 뷰를 조회할 때마다 `CORTEX.COMPLETE` 가 **행 수만큼 다시 실행됩니다.**

```sql
SELECT * FROM ANALYSIS_V WHERE id = 1;   -- 겉보기엔 단순 조회
                                          -- 실제로는 LLM 추론이 돈다
```

즉 **"조회"라고 생각한 동작이 전부 과금 대상**이었습니다.
대시보드가 새로고침될 때마다, 다른 쿼리가 이 뷰를 조인할 때마다, 비용이 발생했습니다.

에이전트 호출 이력에는 이게 안 잡힙니다. 에이전트가 부른 게 아니니까요.

### 가장 뜨끔했던 부분

원인을 파악하는 동안, 저는 그 뷰를 **"조회는 무비용이니까"** 라며 여러 번 조회했습니다.

그 조회들도 전부 과금이었습니다.
원인을 찾는 행위 자체가 원인을 키우고 있었습니다.

## 조치

뷰를 테이블로 materialize 했습니다.

```sql
-- 추론은 적재 시점에 한 번만
CREATE TABLE ANALYSIS_T AS
SELECT
    id,
    raw_text,
    SNOWFLAKE.CORTEX.COMPLETE('...', raw_text) AS summary
FROM SOURCE_TABLE;

-- 이후 조회는 저장된 결과를 읽을 뿐
SELECT * FROM ANALYSIS_T WHERE id = 1;
```

추론 시점을 **조회할 때마다**에서 **적재할 때 한 번**으로 옮긴 것입니다.
결과가 매번 달라질 필요가 없는 데이터였기 때문에 가능했습니다.

## 이 문제의 성질

LLM 함수는 SQL 문법 안에서 일반 함수와 똑같이 생겼습니다.
`UPPER()` 옆에 `CORTEX.COMPLETE()` 를 써도 문법적으로 아무 문제가 없습니다.

그런데 비용 구조는 전혀 다릅니다.

| | 일반 함수 | LLM 함수 |
|---|---|---|
| 실행 비용 | 무시 가능 | **행당 과금** |
| 뷰에 넣으면 | 문제없음 | **조회할 때마다 재실행** |
| 조회자가 아는가 | — | **모른다.** 겉보기엔 그냥 컬럼 |

**뷰를 조회하는 사람은 그 안에 무엇이 들어 있는지 보지 않습니다.**
컬럼 이름이 `summary` 라면 그냥 저장된 값이라고 생각합니다.
비용이 발생한다는 신호가 어디에도 없습니다.

### 어디를 봐야 하나

같은 구조를 찾으려면 뷰 정의를 직접 뒤지는 수밖에 없습니다.

```sql
-- 뷰 정의에 LLM 함수가 들어 있는지 훑기
SELECT table_schema, table_name
FROM information_schema.views
WHERE UPPER(view_definition) LIKE '%CORTEX.%';
```

그리고 나온 뷰마다 물어봐야 합니다.

- 이 뷰를 **누가, 얼마나 자주** 조회하는가
- 결과가 **매번 달라져야 하는가** (아니라면 테이블로 옮길 수 있다)
- 다른 뷰가 **이 뷰를 참조**하고 있는가 (중첩되면 배수로 늘어난다)

## 정리

- **LLM 함수를 뷰 정의에 넣지 말 것.** 뷰는 조회할 때마다 다시 실행된다
- 추론은 **적재 시점에 한 번**. 결과가 고정될 수 있는 데이터라면 테이블로 materialize
- 비용 이상을 볼 때 **에이전트 호출 이력만 보면 안 된다.** 호출 없이 발생하는 비용이 있다
- 설명이 깔끔하게 떨어지면 그때가 **가장 위험**하다. 맞는 요인 하나로 전체를 설명했다고 착각하기 쉽다

마지막 줄이 이번에 남은 것입니다.
"사용량이 늘어서"는 틀린 말이 아니었습니다. 다만 **충분한 설명이 아니었습니다.**
문서를 이미 써놓은 뒤에 이력을 조회한 게 다행이었습니다. 순서가 반대였어야 했지만.
