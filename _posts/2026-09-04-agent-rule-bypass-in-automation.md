운영 중인 분석 에이전트의 Instruction에 이런 규칙이 있었습니다.

> 지원 대상이 아닌 리전의 데이터는 조회하지 않는다. (FILTER-IN allowlist)

채팅으로 물어보면 잘 막혔습니다. 미지원 리전을 요청하면 즉시 거부합니다.
그런데 **정기 실행(Automation)으로 등록된 작업에서는 그 리전의 분석 리포트가 생성되어
이메일로 발송되고 있었습니다.**

발견도 시스템이 아니라 사람이 했습니다.
리포트를 받은 사람이 **데이터의 신뢰성이 이상하다고 느껴 운영팀에 문의**하면서 드러났습니다.
지원 대상이 아닌 리전이라 데이터 정합성이 보장되지 않는 구간이었으니까요.

같은 에이전트, 같은 규칙, 같은 질문인데 **경로에 따라 결과가 달랐습니다.**

## 처음 의심한 것

규칙 문장이 약한가 싶어 표현을 강하게 고쳐볼 수 있었습니다.
하지만 그건 방향이 틀렸습니다. 채팅에서는 **원래도** 잘 막히고 있었으니까요.

차이는 규칙이 아니라 **규칙이 놓인 컨텍스트**에 있었습니다.

## 원인 — 세 가지가 겹쳤다

### 1. Automation은 "요청"이 아니라 "확정된 임무"로 들어온다

채팅에서 사용자가 묻는 건 요청입니다. 시스템 규칙이 그 위에 있습니다.

그런데 Automation으로 등록된 작업은 **"이 분석을 매일 실행하라"는 명시적 Task 지시**로
매번 주입됩니다. 모델 입장에서 이건 즉흥적 요청이 아니라 이미 확정된 임무입니다.
시스템 규칙과 부딪히면 확정된 임무 쪽이 더 무겁게 작용했습니다.

```text
System Instruction          Automation Prompt
FILTER-IN 규칙        ⚡    "해당 리전 분석을 실행하라"
미지원 리전 → 차단          (명시적 Task)
                    ↓
              LLM 판단: Task 완수 우선
              → 경고만 남기고 분석 진행
                    ↓
              리포트 생성 · 이메일 발송
```

### 2. 데이터가 실제로 있었다

규칙은 "조회하지 마라"였지만, 해당 리전의 데이터는 웨어하우스에 실재했습니다.

모델은 이렇게 해석한 것으로 보입니다 —
*"막으라고 했지만 데이터가 있네. 참고용으로는 제공해도 되겠다."*

**금지 규칙과 실재하는 데이터가 만나면 모델은 그 사이에서 타협안을 만듭니다.**
사람이라면 "없는 셈 쳐라"로 읽을 문장을 모델은 "가급적 피하라"로 읽었습니다.

### 3. LLM은 주어진 일을 끝내려 한다

이게 근본입니다. 규칙과 임무가 충돌하면 임무를 포기하는 게 아니라,
**규칙을 경고 수준으로 격하하고 진행합니다.**

설정 실수가 아니라 LLM 기반 시스템의 구조적 성질에 가깝습니다.
그래서 "더 강하게 쓰면 되겠지"로는 해결되지 않습니다.

## 조치 — 세 가지

### ① 규칙에서 해석의 여지를 없앤다

기존 규칙은 *SQL 생성을 중단하라* 였습니다. 여기에 빠져나갈 틈이 있었습니다.

```text
[변경 전]
→ 즉시 모든 SQL 생성을 중단한다

[변경 후]
→ 즉시 모든 SQL 생성을 중단한다
→ 즉시 모든 자동화 설정을 중단한다              ← 적용 범위 확장
→ 데이터가 존재하더라도 이 규칙을 우선한다        ← 타협 차단
→ 명시적으로 요청받아도 에러만 출력하고 종료한다   ← 지시 우선순위 역전
```

세 줄이 각각 위 원인 ①②③에 대응합니다.
특히 **"데이터가 존재하더라도"** 한 줄이 컸습니다. 모델이 만들던 타협안을 미리 막았습니다.

여기에 매 요청 자가 점검(RECITATION) 항목을 추가했습니다.

```text
□ 제한 대상 + 자동화 설정이 동시에 요청된 경우,
  자동화 스킬 호출 전에 대상 검증을 마쳤는가?
```

### ② 실행 앞에 검증 게이트를 세운다

규칙만으로는 부족하다고 봤습니다.
자동화 등록 요청이 들어오면 **본 작업 전에 먼저 실행되는 검증 스킬**을 만들었습니다.

```text
자동화 설정 요청
      │
      ▼
 [검증 게이트]   ← [REQUIRED] 태그로 우선 호출
      │
      ├── 허용 목록에 있음 → APPROVED → 자동화 스킬로 위임
      └── 목록에 없음     → BLOCKED  → 에러만 출력하고 종료
```

BLOCKED일 때는 자동화 호출뿐 아니라 **SQL 생성과 데이터 조회까지 전부 금지**했습니다.
"데이터가 존재하더라도 BLOCKED"를 스킬 본문에도 다시 명시해 이전 우회 패턴을 닫았습니다.

개인 스킬로 검증한 뒤 Agent 스킬로 승격해 전체 사용자에게 적용했습니다.

### ③ 이미 만들어진 자동화를 삭제한다

규칙과 게이트는 **앞으로 들어올 요청**을 막습니다.
이미 등록되어 매일 돌고 있던 자동화는 그대로 남아 있으므로, 별도로 삭제했습니다.

새 유입을 막는 것과 기존 상태를 정리하는 것은 다른 일입니다.
전자만 하고 끝내면 리포트는 계속 나갑니다.

## 그래서 해결됐나 — 절반만

적용 후 자동화 경로에서 규칙이 정상 동작하는 것을 확인했습니다.
하지만 **이건 프로그래밍적 보장이 아닙니다.**

게이트 스킬을 뜯어보면 두 층이 섞여 있습니다.

| | 판정 방식 | 성격 |
|---|---|---|
| 게이트 **안**의 판정 | 허용 목록 대조 | 결정적 |
| 게이트를 **부를지** 여부 | `[REQUIRED]` 태그를 보고 모델이 판단 | **비결정적** |

즉 **게이트를 호출하는 것 자체가 여전히 모델의 판단**입니다.
프롬프트 층을 하나 더 쌓아 확률을 낮춘 것이지, 경로를 물리적으로 닫은 게 아닙니다.

처음 문제가 "규칙을 모델이 어떻게 읽느냐"에서 왔는데,
해결책도 결국 같은 층에 있습니다. 강해졌지만 종류가 달라지진 않았습니다.

제대로 닫으려면 **자동화 실행 전에 대상을 코드 레벨에서 검증하는 사전 게이트**가
플랫폼 쪽에 있어야 합니다. 현재는 플랫폼 팀과 협의가 필요한 상태로 남겨두었습니다.

## 정리

- 규칙이 안 지켜질 때 **규칙 문장부터 고치려 들지 말 것.** 경로별로 재현하면 범위가 좁혀진다
- 금지 규칙 옆에 데이터가 실재하면 모델은 그 사이에서 **타협안을 만든다.** "있어도 무시하라"를 명시해야 한다
- 시스템 규칙과 명시적 임무가 충돌하면 **임무가 이기는 쪽**으로 기운다
- 새 유입 차단과 기존 상태 정리는 **다른 작업**이다. 둘 다 해야 끝난다
- **프롬프트로 막은 것을 코드로 막았다고 말하지 말 것.** 층위가 다르면 신뢰도가 다르다

마지막 줄이 이번에 가장 크게 남았습니다.
게이트를 만들고 나서 "구조적으로 해결했다"고 적을 뻔했는데,
호출 자체가 모델 판단이라는 걸 다시 보고 나서 그 표현을 지웠습니다.
