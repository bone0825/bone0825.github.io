0 이 문서를 읽는 방법과 기본 용어

이 문서는 무엇을 다루나요?

Snowflake는 회사의 데이터를 클라우드(인터넷 상의 서버)에 저장하고 분석하는 데이터 플랫폼입니다. 그 안에는 Cortex라는 이름의 AI 기능 묶음이 있고, 그중 하나가 이 문서의 주인공인 Cortex Search Service입니다. 한 문장으로 말하면 "Snowflake에 저장된 글(문서, 상담 기록, 매뉴얼 등)을 사람이 말하는 방식으로 검색해 주는 기능"입니다.

회사에 수십만 건의 고객 상담 기록이 있다고 상상해 보세요. 누군가 "인터넷이 자꾸 끊겨요"라고 검색하면, "네트워크 접속 불안정"이라고 적힌 기록까지 찾아 주어야 진짜 쓸모 있는 검색입니다. 단어가 달라도 뜻이 같으면 찾아 주는 검색, 그것을 만들어 주는 도구가 Cortex Search입니다.

Part I

기술 원리 Deep Dive

Cortex Search 안에서 검색이 실제로 어떻게 일어나는지, 여섯 가지 핵심 기술을 하나씩 따로 떼어 설명합니다. 순서대로 읽으면 앞 장의 내용이 다음 장의 재료가 됩니다.

1 검색은 어떻게 동작하는가

TL;DR

검색에는 "글자가 같은 것을 찾는 방식"(키워드 검색)과 "뜻이 비슷한 것을 찾는 방식"(의미 검색)이 있습니다. 각각 장단점이 있어서, Cortex Search는 둘을 함께 쓰고 마지막에 한 번 더 순위를 다듬습니다.

두 가지 검색 방식

도서관에서 "인터넷이 안 될 때 해결법"이 적힌 책을 찾는다고 생각해 보세요.
방법 1 — 책 뒤 색인에서 "인터넷"이라는 단어가 나오는 페이지를 모두 찍어 본다. 정확하지만, "네트워크"라고 적힌 페이지는 놓칩니다.
방법 2 — 사서에게 "인터넷이 안 될 때요"라고 말하면, 사서는 "네트워크 장애 대응" 책을 꺼내 줍니다. 단어가 달라도 뜻을 알아듣기 때문입니다.

키워드 검색 (Keyword Search)의미 검색 (Semantic / Vector Search)
찾는 기준검색어와 글자가 같은 단어가 문서에 있는가검색어와 뜻이 비슷한 내용이 문서에 있는가
잘하는 것제품 코드 "AG1001", 사람 이름, 정확한 용어동의어, 표현이 다른 같은 뜻 ("인터넷 장애" ≈ "네트워크 다운")
못하는 것단어가 다르면 못 찾음정확한 코드나 고유명사에 약함
핵심 기술역색인(Inverted Index) + BM25 점수 → 4장임베딩(Embedding) + 벡터 검색(ANN) → 2, 3장
역사1990년대부터 쓰인 검증된 방식 (초기 구글 이전)2018년 이후 딥러닝 발전으로 실용화

Cortex Search가 택한 답: 둘 다 쓰고, 한 번 더 고른다

두 방식은 서로의 약점을 보완합니다. 그래서 Cortex Search는 검색 한 번에 아래 세 단계를 자동으로 수행합니다. 이것을 하이브리드 검색(Hybrid Search)이라고 부릅니다. 각 단계의 자세한 원리는 2~6장에서 다룹니다.

  1. 의미 검색 (Vector Search)검색어의 "뜻"과 가까운 문서를 찾습니다. → 2장 임베딩, 3장 ANN
  2. 키워드 검색 (Keyword Search)검색어와 "글자"가 일치하는 문서를 찾습니다. → 4장 BM25
  3. 재순위화 (Semantic Reranking)1, 2번에서 모은 후보를 더 꼼꼼한 모델이 다시 읽고 최종 순서를 정합니다. → 6장

그리고 이렇게 찾은 문서를 AI(LLM)에게 넘겨 답변을 만들게 하는 것이 RAG입니다. → 7장

2 Deep Dive ① Embedding — 글을 숫자로 바꾸기

TL;DR

임베딩(Embedding)은 글(단어, 문장, 문서)을 숫자 목록(벡터)으로 바꾸는 기술입니다. 뜻이 비슷한 글은 비슷한 숫자 목록이 되도록 만들어져 있어서, 컴퓨터가 "이 두 문장은 뜻이 가깝다"를 계산할 수 있게 됩니다. 의미 검색의 가장 밑바탕이 되는 기술입니다.

왜 글을 숫자로 바꿔야 하나요?

컴퓨터는 글자를 "그림"처럼 저장할 뿐, 그 뜻은 모릅니다. "인터넷 장애"와 "네트워크 다운"은 컴퓨터에게 단 한 글자도 같지 않은, 완전히 다른 문자열입니다. 하지만 컴퓨터는 숫자 계산은 아주 잘합니다. 그래서 "뜻"을 숫자로 바꿔 놓으면, 두 숫자가 얼마나 가까운지 계산하는 방식으로 뜻이 얼마나 비슷한지 알 수 있습니다.

지도를 떠올려 보세요. 서울(37.5, 127.0)과 인천(37.4, 126.7)은 좌표 숫자가 비슷하니 가깝고, 부산(35.1, 129.0)은 숫자가 달라서 멀다는 것을 계산으로 알 수 있습니다.
임베딩은 "뜻의 지도"를 만드는 일입니다. 모든 문장에 좌표를 붙여서, 뜻이 비슷한 문장끼리 지도 위에서 가까이 놓이게 합니다. 다만 이 지도는 2차원(가로, 세로)이 아니라 768차원, 1,024차원처럼 숫자가 수백 개 필요한 지도입니다. 사람이 그림으로 그릴 수는 없지만 계산 원리는 똑같습니다.

벡터란 무엇인가요?

벡터(Vector)는 그냥 "숫자를 순서대로 나열한 것"입니다. (3, 5)는 숫자 2개짜리 벡터, (0.82, 0.15, 0.93, ...)처럼 768개가 나열되면 768차원 벡터입니다. 여기서 차원(Dimension)은 "숫자가 몇 개인가"를 뜻합니다. 차원이 많을수록 더 미세한 뜻의 차이를 표현할 수 있지만, 저장 공간과 계산량도 늘어납니다.

벡터(Vector)란? 수학에서 벡터는 "방향과 크기를 가진 양"이지만, 여기서는 간단히 숫자들의 나열(배열)이라고 생각하면 됩니다. 예를 들어 [0.82, 0.15, 0.93]은 3개의 숫자로 이루어진 벡터입니다. 임베딩 벡터는 이런 숫자가 768개 또는 1024개 나열된 것입니다.
Embedding: 텍스트 → 벡터 변환 예시
"인터넷 연결 문제"
→
[0.82, 0.15, 0.93, -0.21, 0.67, ...] (768개 숫자)
"네트워크 다운"
→
[0.79, 0.18, 0.90, -0.19, 0.63, ...] ← 유사한 벡터!

위 예시에서 "인터넷 연결 문제"와 "네트워크 다운"은 단어가 하나도 겹치지 않지만 벡터 값은 비슷합니다. 반대로 "요금 청구 오류"는 완전히 다른 값이 나옵니다. 이 차이를 숫자로 재는 방법이 다음에 나오는 코사인 유사도입니다. (예시의 숫자는 이해를 돕기 위한 가상의 값입니다.)

얼마나 비슷한지 재는 방법: 코사인 유사도

두 벡터가 얼마나 비슷한지 재는 대표적인 방법이 코사인 유사도(Cosine Similarity)입니다. 벡터를 원점에서 출발하는 화살표라고 생각하면, 코사인 유사도는 두 화살표 사이의 각도가 얼마나 좁은지를 나타냅니다.

같은 방향 (각도 0°) → 유사도 1.0 (뜻이 거의 같음)
직각 (각도 90°) → 유사도 0.0 (관련 없음)
반대 방향 (각도 180°) → 유사도 -1.0 (뜻이 반대)

예를 들어 2차원에서 A = (1, 1)과 B = (2, 2)는 길이는 다르지만 방향이 완전히 같으므로 유사도가 1.0입니다. A = (1, 1)과 C = (1, -1)은 직각이므로 0입니다. 실제로는 768개 숫자로 같은 계산을 하지만 원리는 동일합니다. "길이(글의 길이)는 무시하고 방향(뜻)만 본다"는 점이 코사인 유사도의 장점입니다.

2D 벡터 공간 시각화 (실제로는 768~1024 차원)

위 그림은 768차원 공간을 이해하기 쉽게 2차원으로 그린 것입니다. 뜻이 비슷한 문장들이 같은 영역에 모여 있고, 검색어 "인터넷이 안 돼요"의 벡터(노란 점)는 "네트워크/연결 문제 영역"을 향하고 있습니다. 그 방향에 있는 문서들이 검색 결과가 됩니다.

차원이 많을수록 무조건 좋을까? — Trade-off

차원이 높을수록 표현력은 올라가지만 무조건 좋은 것은 아닙니다. 저장 공간, 검색 속도, 임베딩 비용이 함께 늘어납니다. 또한 차원이 지나치게 높으면 차원의 저주(Curse of Dimensionality)라는 현상이 생길 수 있습니다. 숫자가 너무 많아지면 모든 벡터 사이의 거리가 다 비슷해져서, 오히려 "가깝다/멀다"를 구분하기 어려워지는 현상입니다. 따라서 용도에 맞는 적절한 차원 수를 고르는 것이 핵심입니다.

핵심: "차원이 높을수록 무조건 좋다"는 오해입니다. 768D이면 인간 언어의 미세한 뉘앙스 차이까지 충분히 구분할 수 있으며, 1024D는 다국어처럼 더 복잡한 의미 체계를 다뤄야 할 때 선택합니다. 용도에 맞는 적절한 크기를 선택하는 것이 비용과 품질 모두에서 최선입니다.

임베딩은 누가 만들어 주나요? — 임베딩 모델

글을 벡터로 바꾸는 일은 임베딩 모델(Embedding Model)이라는 AI 프로그램이 합니다. 이 모델은 인터넷의 방대한 글을 미리 읽으면서 "어떤 단어들이 함께 자주 쓰이는가", "어떤 문장들이 같은 뜻인가"를 학습해 두었습니다. 이렇게 미리 학습해 둔 것을 사전 학습(Pre-trained)이라고 하고, 그 내부 구조로 가장 널리 쓰이는 것이 Transformer입니다.

Transformer 트랜스포머
2017년에 나온 AI 모델 구조. 문장 안의 단어들이 서로 어떤 관계인지(어떤 단어가 어떤 단어를 가리키는지)를 한꺼번에 살펴보는 어텐션(Attention) 방식이 핵심입니다. ChatGPT의 "T"도 Transformer입니다.
파라미터 Parameters, params
모델 내부의 조절 값(숫자)의 개수. 학습이란 이 숫자들을 좋은 값으로 맞추는 과정입니다. 110M(1억 1천만 개) 모델은 작고 빠르고, 568M(5억 6천만 개) 모델은 크고 정교합니다.
컨텍스트 윈도우 Context Window
모델이 한 번에 읽을 수 있는 글의 최대 길이(토큰 수). 512 토큰 모델에 더 긴 글을 넣으면 뒷부분이 잘립니다. 그래서 긴 문서는 청크로 나눕니다.

Cortex Search에서는 어떻게 쓰이나요?

Cortex Search에서의 임베딩:
  • 서비스 생성 시 소스 테이블의 텍스트를 자동으로 임베딩 (수동 파이프라인 불필요)
  • 검색 쿼리도 같은 모델로 임베딩하여 Vector Search 수행
  • 변경된 Row만 재임베딩하는 Incremental 방식으로 비용 최적화
  • 임베딩 모델은 서비스 생성 시 선택하며 변경 불가
  • Custom Vector Embedding도 지원 (외부 모델 벡터 직접 사용)
Q. 한국어도 임베딩이 되나요?

모델에 따라 다릅니다. 영어만 학습한 모델(예: arctic-embed-m-v1.5)에 한국어를 넣으면 뜻을 제대로 잡지 못합니다. 한국어 데이터라면 다국어(Multilingual) 모델을 골라야 합니다. 모델 목록은 11장에서 비교합니다.

Q. 왜 임베딩 모델은 나중에 바꿀 수 없나요?

모델이 다르면 같은 문장도 완전히 다른 벡터가 됩니다. 즉 A 모델로 만든 문서 벡터와 B 모델로 만든 검색어 벡터는 비교할 수 없습니다. 모델을 바꾸려면 모든 문서의 벡터를 처음부터 다시 만들어야 하므로, Cortex Search는 서비스를 새로 만들도록 하고 있습니다.

Q. "Custom Vector Embedding"은 무슨 뜻인가요?

Snowflake가 제공하는 모델 대신, 내가 다른 곳(OpenAI, Cohere 등)에서 이미 만들어 둔 벡터를 그대로 가져와 쓰는 기능입니다. 벡터를 이미 갖고 있다면 임베딩 비용을 다시 낼 필요가 없습니다. 12장 Multi-Index에서 다시 나옵니다.

3 Deep Dive ② Vector Search & ANN — 비슷한 벡터를 빨리 찾기

TL;DR

문서 수백만 개의 벡터 중에서 검색어 벡터와 가장 가까운 것을 찾는 일이 벡터 검색입니다. 하나하나 다 비교하면 너무 느리기 때문에, 미리 정리해 두고 근처만 뒤지는 ANN(근사 최근접 이웃) 기법을 씁니다. 정확도를 아주 조금 양보하고 속도를 수백 배 얻는 거래입니다.

"가장 가까운 이웃"을 찾는다는 것

2장에서 모든 문서가 벡터(뜻의 좌표)를 갖게 되었습니다. 이제 검색어도 같은 모델로 벡터로 바꾸면, 검색은 "검색어 벡터와 가장 가까운 문서 벡터 K개를 찾는 문제"가 됩니다. 이것을 최근접 이웃 탐색(Nearest Neighbor Search)이라고 하고, 상위 K개를 고르므로 Top-K라고도 부릅니다.

"지금 내 위치에서 가장 가까운 카페 5곳"을 찾는다고 해 봅시다.
정확한 방법: 전국의 카페 10만 곳까지의 거리를 전부 계산해서 정렬한다. 확실하지만 오래 걸립니다.
영리한 방법: 지도를 미리 구역으로 나눠 두고, 내가 있는 구역과 옆 구역만 본다. 아주 드물게 구역 경계 너머의 카페를 놓칠 수 있지만, 거의 항상 같은 답을 훨씬 빨리 얻습니다. 이것이 ANN입니다.

Exact Search vs ANN (Approximate Nearest Neighbor)
Exact (Brute-Force) Search
모든 벡터와 거리를 계산하여 가장 가까운 것을 찾음
100% 정확하지만 매우 느림
100만 문서 × 768차원 = 수십 초 소요
ANN (Approximate) Search
벡터를 클러스터/그래프로 사전 구조화하여 쿼리 근처 영역만 탐색
99%+ 정확도로 수 밀리초 내 응답
100만 문서에서도 10~50ms 이내

대표적인 ANN 방법 두 가지

IVF

IVF (Inverted File Index)

벡터들을 미리 몇 백~몇 천 개의 구역(클러스터)으로 묶어 두고, 검색어와 가까운 구역 몇 개만 뒤집니다. 위 카페 비유와 가장 비슷한 방식입니다.

HNSW

HNSW (Hierarchical Navigable Small World)

벡터들을 서로 연결한 여러 층의 지도를 만듭니다. 위층은 고속도로처럼 큰 범위를 빠르게 이동하고, 아래층으로 내려갈수록 국도, 골목처럼 촘촘해져 목적지에 정확히 도착합니다. 현재 가장 널리 쓰이는 방식입니다.

왜 "Approximate"인가? 정확한 최근접 이웃을 100% 보장하지는 않지만, 99% 이상의 정확도를 밀리초 단위로 달성합니다. 수백만 건의 벡터에서 실시간 검색을 가능하게 하는 핵심 기술입니다. 대표적인 ANN 알고리즘으로는 HNSW(Hierarchical Navigable Small World), IVF(Inverted File Index) 등이 있으며, Cortex Search는 이를 내부적으로 자동 관리합니다.
왜 100%가 아니어도 괜찮을까요? 검색에서 우리가 원하는 것은 "관련 있는 문서 상위 몇 개"입니다. 99.x% 정확도의 ANN이 놓치는 것은 대개 순위 경계에 있는, 있어도 없어도 큰 차이 없는 문서입니다. 반면 속도는 수십 초에서 수십 밀리초로, 수백~수천 배 빨라집니다. 사용자가 검색 버튼을 누르고 30초를 기다릴 수는 없으니, 이 거래는 충분히 남는 장사입니다. Cortex Search는 어떤 ANN 알고리즘을 어떻게 설정할지 사용자가 고민할 필요 없이 내부에서 자동으로 관리합니다.

4 Deep Dive ③ Keyword Search & BM25 — 단어 일치에 점수 매기기

TL;DR

키워드 검색은 검색어에 들어 있는 단어가 실제로 등장하는 문서를 찾습니다. 빨리 찾기 위해 역색인이라는 자료 구조를 쓰고, 여러 문서 중 어느 것이 더 관련 있는지는 BM25라는 점수 공식으로 정합니다.

역색인(Inverted Index): 단어 → 문서 번호

문서 100만 건을 매번 처음부터 읽어 "인터넷"이 있는지 확인하면 너무 느립니다. 그래서 미리 "어떤 단어가 어느 문서에 나오는가"를 표로 만들어 둡니다. 문서에서 단어를 찾는 방향을 거꾸로(단어에서 문서를 찾도록) 만들었기 때문에 역(Inverted)색인이라고 부릅니다.

교과서 맨 뒤의 "찾아보기"가 바로 역색인입니다. "광합성 ... 45, 112쪽"이라고 적혀 있으면 책을 다 읽지 않고도 바로 그 페이지로 갈 수 있습니다.

단어등장하는 문서 번호비고
인터넷#3, #17, #42검색어에 포함 → 후보
연결#3, #42, #88, #90검색어에 포함 → 후보
문제#3, #5, #17, #42, #61, ... (매우 많음)흔한 단어 → 점수 낮게
요금#5, #61검색어에 없음 → 무시

"인터넷 연결 문제"를 검색하면 세 단어의 목록을 겹쳐 봅니다. 문서 #3과 #42는 세 단어가 모두 있고, #17은 두 개, #88은 한 개입니다. 그런데 "모두 있다"만으로는 순위를 정하기 부족합니다. 어느 문서가 더 관련 깊은지 점수를 매겨야 하는데, 그 공식이 BM25입니다.

BM25: 관련성을 점수로 바꾸는 공식

BM25(Best Matching 25)는 정보 검색 분야에서 수십 년간 쓰여 온 표준 점수 공식입니다. 복잡한 수식 대신 핵심 아이디어 세 가지만 알면 충분합니다.

BM25 Scoring - 핵심 원리 3가지
TF
Term Frequency
검색어가 문서에 많이 등장할수록 높은 점수.
단, 반복 횟수에 따른 점수 증가가 포화(saturation)됨
"인터넷" 1회 = 0.8점
"인터넷" 5회 = 0.95점 (포화)
IDF
Inverse Document Frequency
전체 문서에서 드물게 등장하는 단어일수록 높은 점수.
"the", "is" 같은 흔한 단어는 낮은 점수
"인터넷" (10% 문서) = 높은 IDF
"문제" (80% 문서) = 낮은 IDF
DL
Document Length Norm.
짧은 문서에서 검색어가 등장하면 더 높은 점수.
긴 문서는 우연히 매칭될 확률이 높으므로 보정
50단어 문서에 "인터넷" = 높은 점수
5,000단어 문서에 "인터넷" = 낮은 점수
세 원리를 한 문장으로: "검색어가 여러 번 나오고(TF), 그 검색어가 흔하지 않은 단어이며(IDF), 문서가 짧아서 그 단어가 문서의 핵심일 가능성이 높으면(DL) 점수가 높다." 단, TF는 무한히 커지지 않습니다. 같은 단어를 100번 반복해 넣어도 5번 넣은 것과 점수가 거의 같도록 포화(saturation)시켜, 단어 반복으로 순위를 조작하는 것을 막습니다.

"어제부터 인터넷이 연결 안 되는 문제를 해결해주세요"
TF: 3개 단어 모두 매칭 | IDF: "인터넷" 높음 | DL: 짧은 문서

"인터넷 속도가 느린 문제를 신고합니다"
TF: 2개 단어 매칭 | IDF: "인터넷" 높음 | DL: 짧은 문서

3위
"다양한 네트워크 연결 방법과 보안 설정에 대한 종합 가이드... (5,000단어)"
TF: 1개 단어 매칭 | IDF: "연결" 낮음 | DL: 매우 긴 문서 → 보정

Score = TF 포화 × IDF × DL 보정 (각 검색어별 합산)

위 점수(8.7, 5.2, 1.3)는 원리를 보여 주기 위한 예시 값입니다. 실제 값은 전체 문서 집합의 통계에 따라 달라집니다.

BM25의 한계 (Cortex Search가 Hybrid로 보완하는 이유): BM25는 정확한 단어 매칭에만 의존합니다. "인터넷 장애"로 검색하면 "네트워크 다운"은 매칭되지 않습니다 (동의어 처리 불가). 이것이 Cortex Search가 BM25(Keyword Search)와 Vector Search(의미 검색)를 결합(Hybrid)하는 이유입니다.

5 Deep Dive ④ Hybrid Search — 두 방식을 합치기

TL;DR

하이브리드 검색은 의미 검색(2~3장)과 키워드 검색(4장)을 동시에 실행해서 후보를 모으고, 리랭커(6장)로 최종 순서를 정하는 3단계 파이프라인입니다. Cortex Search의 핵심 구조이며, 사용자는 별도로 조정할 것 없이 기본으로 이 방식이 동작합니다.

왜 합쳐야 하나요? — 정확도와 재현율

검색 품질을 말할 때 자주 쓰는 두 단어가 있습니다.

Precision 정밀도, 정확도
"검색 결과로 나온 것 중에 진짜 관련 있는 것의 비율". 엉뚱한 결과가 섞이면 Precision이 낮습니다.
Recall 재현율
"관련 있는 문서 전체 중에 실제로 검색 결과에 포함된 것의 비율". 있어야 할 문서를 놓치면 Recall이 낮습니다.

낚시 그물로 비유하면, Precision은 "잡은 것 중 원하는 물고기 비율"(쓰레기가 얼마나 안 섞였나), Recall은 "바다에 있는 원하는 물고기 중 얼마나 건졌나"입니다. 키워드 검색은 정확한 단어만 잡으니 Precision은 높지만 표현이 다른 문서를 놓쳐 Recall이 낮고, 의미 검색은 넓게 건져 Recall은 높지만 엉뚱한 것이 섞여 Precision이 낮아질 수 있습니다. 둘을 합치면 넓게 건지고(Recall) 걸러내는(Precision) 두 가지를 모두 얻습니다.

6 Deep Dive ⑤ Semantic Reranking — 최종 순위 다시 매기기

TL;DR

1차 검색은 빠르게 "대충 관련 있는 후보"를 모으는 단계입니다. 리랭킹(Reranking)은 그 후보 수십 개만을 대상으로, 검색어와 문서를 한 쌍으로 함께 읽는 더 정밀한 모델(Cross-Encoder)이 순위를 다시 매기는 단계입니다. 느리지만 정확한 모델을 소수 후보에만 쓰기 때문에 속도와 품질을 둘 다 잡습니다.

채용 과정과 비슷합니다. 지원자 1,000명의 서류를 한 명씩 1시간 면접할 수는 없으니, 먼저 서류 심사로 빠르게 20명을 고르고(1차 검색), 그 20명만 면접을 봐서 최종 순위를 정합니다(리랭킹). 면접이 훨씬 정확하지만 시간이 오래 걸리므로 소수에게만 씁니다.
도서관으로 바꿔 말하면, 1차 검색은 "관련 있을 만한 책 10권을 빠르게 골라 오는 것", 리랭킹은 "그 10권을 한 권씩 펼쳐 보고 질문에 가장 잘 맞는 순서로 다시 꽂는 것"입니다.

왜 1차 검색만으로는 부족한가요?

Vector Search는 검색어와 문서를 각각 따로 벡터로 바꾼 뒤 비교합니다. 문서 벡터는 미리 만들어 두었기 때문에 빠르지만, 검색어와 문서가 "서로를 보면서" 비교된 것은 아니어서 세밀한 뉘앙스(예: "정책 안내"와 "재설정 방법"의 차이)를 놓칠 수 있습니다. Keyword Search는 단어 빈도만 보기 때문에 뜻을 이해하지 못합니다.

Bi-Encoder vs Cross-Encoder

이 차이를 만드는 것이 모델의 구조입니다.

Bi-Encoder 바이 인코더, 1차 검색용
검색어와 문서를 따로따로 벡터로 바꾸고, 나중에 두 벡터를 비교합니다. 문서 벡터를 미리 계산해 둘 수 있어 수백만 건도 빠르게 처리합니다. 2장의 임베딩 모델이 바로 Bi-Encoder입니다.
Cross-Encoder 크로스 인코더, 리랭커용
검색어와 문서를 하나로 이어 붙여 함께 모델에 넣습니다. 모델 내부의 어텐션이 검색어 단어와 문서 단어를 직접 대응시켜 보기 때문에 훨씬 정확합니다. 하지만 검색어가 들어와야 계산할 수 있어 미리 준비해 둘 수 없고, 문서 하나마다 모델을 한 번씩 돌려야 하므로 느립니다.
Cross-Encoder란? 쿼리와 문서를 하나의 입력으로 합쳐서 AI 모델에 넣는 방식입니다. 마치 시험관이 "이 질문과 이 답안을 나란히 놓고 직접 비교"하는 것과 같습니다. Bi-Encoder(임베딩)가 쿼리와 문서를 따로따로 처리하는 것과 대비됩니다. 정밀하지만 느리기 때문에, 전체 문서가 아닌 1차 검색으로 추려낸 소수의 후보에만 적용합니다.

7 Deep Dive ⑥ RAG — 검색 결과로 AI 답변 만들기

TL;DR

RAG(Retrieval-Augmented Generation)는 AI(LLM)에게 질문만 던지는 대신, 먼저 관련 문서를 검색해서 함께 건네주고 그 문서를 근거로 답하게 하는 방법입니다. AI가 모르는 사내 정보로 답할 수 있게 하고, 지어낸 답(환각)을 크게 줄여 줍니다. Cortex Search는 이 과정의 "검색(Retrieval)" 부분을 담당합니다.

먼저, LLM이란 무엇인가요?

LLM(Large Language Model, 대형 언어 모델)은 ChatGPT, Claude처럼 사람의 말을 이해하고 글을 만들어 내는 AI입니다. 인터넷의 엄청난 양의 글을 읽고 "이런 문장 뒤에는 보통 어떤 말이 이어지는가"를 학습해서, 질문을 받으면 그럴듯한 다음 말을 이어 나가는 방식으로 답을 만듭니다. LLM에게 건네는 입력 문장을 프롬프트(Prompt), 프롬프트 안에 참고 자료로 넣어 주는 내용을 컨텍스트(Context)라고 합니다.

LLM만으로는 부족한 이유

LLM은 놀랍도록 유창하지만, 작동 방식 때문에 생기는 근본적인 한계가 네 가지 있습니다.

H1

Hallucination (환각)

LLM이 사실처럼 보이지만 실제로는 틀린 정보를 자신 있게 생성합니다. "그럴듯한 거짓말"을 합니다.

H2

Knowledge Cutoff (학습 시점 한계)

모델 학습 이후의 정보를 모릅니다. "2024년 Q4 실적은?"에 답할 수 없습니다.

H3

No Access to Private Data

회사 내부 문서, 사내 정책, 고객 데이터 등 비공개 데이터에 접근할 수 없습니다.

H4

No Source Citation

답변의 근거를 제시하지 못합니다. "어디서 그 정보를 가져왔는지" 확인할 수 없습니다.

LLM만 쓰는 것은 "기억만으로 시험을 보는 것"입니다. 아는 것은 잘 쓰지만, 모르는 문제도 그럴듯하게 써 버리고(환각), 시험 범위 이후에 배운 내용(최신 정보)이나 우리 회사 내부 자료(비공개 데이터)는 알 수가 없습니다.
RAG는 "오픈북 시험"입니다. 문제를 받으면 먼저 책(지식 베이스)에서 관련 페이지를 찾아 펼쳐 놓고(Retrieval), 그 페이지를 보면서(Augmentation) 답을 씁니다(Generation). 답에 "몇 페이지 참고"라고 출처도 적을 수 있습니다.

RAG는 이 모든 문제를 한 번에 완화합니다. 검색 엔진이 관련 문서를 먼저 찾고, 그 문서를 LLM에게 컨텍스트로 제공하여 사실에 기반한(grounded) 답변을 만들게 합니다. "grounded"는 "근거에 발을 붙인"이라는 뜻입니다.

RAG Architecture - Complete Flow
1
User Query (사용자 질문)
"우리 회사 원격근무 정책에서 해외 근무가 가능한가요?"
2

Hybrid Search (Vector + Keyword + Reranker)로 지식 베이스에서 관련 문서 Top-K 검색
Retrieved Context Chunks:

[Chunk 2] "2024년 원격근무 가이드: 장기 해외 근무 시 현지 법률 검토가 의무적이며, 보안 VPN 사용이 필수입니다..."
3

System Prompt + Retrieved Context + User Query를 하나의 프롬프트로 조합
Constructed Prompt:
[System] 아래 컨텍스트를 기반으로 정확하게 답변하세요.
         근거가 없으면 "정보가 없습니다"라고 답변하세요.

[Context] {Chunk 1} {Chunk 2}

[User] 우리 회사 원격근무 정책에서 해외 근무가 가능한가요?
4

LLM이 컨텍스트를 참고하여 사실에 기반한(grounded) 답변을 생성
5

"네, 해외 근무가 가능합니다. 원격근무 정책 v3.2에 따르면 HR 승인 후 최대 90일까지 해외 근무가 허용됩니다. 다만, 세금 관련 사전 확인과 현지 법률 검토가 필요하며, 보안 VPN 사용이 필수입니다."
Sources: 원격근무 정책 v3.2 | 2024년 원격근무 가이드

R-A-G, 세 글자의 뜻

R
Retrieval
지식 베이스에서 질문과 관련된 문서/구절을 검색합니다. Cortex Search의 Hybrid Search가 이 역할을 수행합니다.
A
Augmentation
검색된 문서를 LLM의 프롬프트에 컨텍스트로 추가합니다. LLM이 참고할 수 있는 근거를 제공합니다.
G
Generation
LLM이 컨텍스트를 기반으로 답변을 생성합니다. 사실에 근거한(grounded) 응답과 출처를 함께 반환합니다.

Snowflake에서 RAG 만들기 (Cortex Search + AI_COMPLETE)

Snowflake에서는 Cortex Search가 Retrieval을, AI_COMPLETE라는 SQL 함수가 Generation(LLM 호출)을 담당합니다. 아래는 SQL 두 문장으로 RAG를 구현한 예시입니다. 코드가 낯설어도 괜찮습니다. 바로 아래에 한 줄씩 풀어 설명합니다. 

-- Snowflake RAG 구현 예시 (SQL)

-- Step 1: Cortex Search로 관련 문서 검색 (Retrieval)
SET context = (
  SELECT PARSE_JSON(
    SNOWFLAKE.CORTEX.SEARCH_PREVIEW(
      'my_db.my_schema.policy_search_service',
      '{"query": "해외 근무 정책", "columns": ["content"], "limit": 3}'
    )
  )['results']::VARCHAR
);

-- Step 2: 검색 결과를 컨텍스트로 LLM에 전달 (Augmentation + Generation)
SELECT AI_COMPLETE(
  'mistral-large2',
  CONCAT(
    '아래 컨텍스트를 기반으로 질문에 답변하세요. ',
    '근거가 없으면 "정보가 없습니다"라고 답하세요.\n\n',
    '[컨텍스트]\n', $context, '\n\n',
    '[질문] 해외 근무가 가능한가요?'
  )
) AS rag_response;

SET context = ( ... )괄호 안의 결과를 context라는 이름의 변수(임시 저장 공간)에 담아 둡니다.
SNOWFLAKE.CORTEX.SEARCH_PREVIEW(...)SQL 안에서 Cortex Search 서비스를 호출하는 함수. 첫 인자는 서비스 이름, 둘째 인자는 JSON 형식의 검색 조건입니다.
"query": "해외 근무 정책"검색어.
"columns": ["content"]결과에서 돌려받을 컬럼. 여기서는 문서 본문(content)만.
"limit": 3상위 3건만 가져옵니다 (Top-K에서 K=3).
PARSE_JSON(...)['results']돌아온 JSON 글자를 해석해서 그중 results(검색 결과 목록) 부분만 꺼냅니다.
AI_COMPLETE('mistral-large2', ...)LLM을 호출하는 함수. 첫 인자는 사용할 모델 이름, 둘째 인자는 프롬프트(질문 전체). (예전 이름 SNOWFLAKE.CORTEX.COMPLETE도 동작합니다.)
CONCAT(...)여러 글자 조각을 이어 붙여 하나의 프롬프트를 만듭니다. 지시문 + 검색 결과($context) + 질문 순서입니다.
'근거가 없으면 "정보가 없습니다"라고 답하세요'환각을 막는 핵심 지시. 컨텍스트에 없는 내용은 지어내지 말라고 미리 못 박습니다.
AS rag_response결과 컬럼의 이름을 rag_response로 붙입니다.
Cortex Agent를 사용하면 더 간단합니다: Cortex Agent에 Cortex Search를 Tool로 연결하면 위의 검색-조합-생성 과정이 자동으로 수행됩니다. 개발자는 Agent 설정(YAML)만 작성하면 됩니다. Agent가 질문 의도를 분석하고, 적절한 검색 쿼리를 구성하고, 결과를 기반으로 답변을 생성합니다.

8 Overview — Cortex Search Service란

TL;DR

Cortex Search Service는 Snowflake 안에 내장된 완전 관리형 하이브리드 검색 엔진입니다. Part I에서 본 임베딩 → 벡터/키워드 검색 → 리랭킹 과정을 사용자가 직접 구축하지 않아도, 테이블 하나를 지정하면 Snowflake가 전부 알아서 처리합니다.

Cortex Search Service는 Snowflake에 내장된 완전 관리형(Fully Managed) 하이브리드 검색 엔진입니다. 벡터 검색(Semantic Search)과 키워드 검색(Keyword Search)을 결합하고, Semantic Reranking까지 자동으로 수행하여 별도의 벡터 데이터베이스나 외부 검색 인프라 없이도 고품질 검색 서비스를 구축할 수 있습니다.

Part I의 기술을 직접 구현하려면 임베딩 모델 서버, 벡터 데이터베이스, 키워드 검색 엔진, 리랭커 서버를 각각 설치하고, 데이터가 바뀔 때마다 다시 임베딩하는 프로그램까지 짜야 합니다. Cortex Search는 이 모든 것을 "이 테이블의 이 컬럼을 검색 가능하게 해 줘"라는 SQL 한 문장으로 대신해 줍니다. 전기를 쓰려고 발전소를 짓지 않듯, 검색을 쓰려고 검색 인프라를 짓지 않게 해 주는 것입니다.

Cortex Search가 해결하는 문제

검색 시스템을 직접 만들 때 부딪히는 네 가지 어려움과, Cortex Search가 이를 어떻게 없애 주는지입니다.

DG

Data Gravity

데이터가 이미 Snowflake에 있으므로 외부 벡터 DB로 복사할 필요 없음. 데이터 이동 없이 검색 서비스 구축

EP

Embedding Pipeline

임베딩 생성, 인덱싱, 갱신을 자동화. 별도 ML Ops 파이프라인 구축 불필요

SG

Security & Governance

Snowflake RBAC, Network Policy, Audit Logging이 그대로 적용. 데이터가 외부로 나가지 않음

FR

Freshness

TARGET_LAG 설정으로 소스 테이블 변경 시 자동 Incremental Refresh. 항상 최신 데이터 검색

Data Gravity 데이터 중력
데이터가 크고 많아지면 옮기기가 점점 어려워져서, 도구가 데이터 쪽으로 끌려온다는 비유. 수 TB의 데이터를 외부 검색 서버로 복사하는 대신, 데이터가 있는 Snowflake 안에서 검색하는 것이 훨씬 쉽고 안전합니다.
ML Ops 파이프라인 Machine Learning Operations
AI 모델을 실제 서비스에서 계속 돌리기 위한 자동화 작업 묶음. 데이터가 바뀌면 다시 임베딩하고, 실패하면 재시도하고, 모델 서버를 관리하는 일 등. 이런 파이프라인을 만들고 유지하는 데 보통 전담 인력이 필요합니다.
RBAC Role-Based Access Control, 역할 기반 접근 제어
"누가 어떤 데이터를 볼 수 있는가"를 역할(Role) 단위로 정하는 보안 방식. Snowflake에 이미 설정된 권한이 검색 서비스에도 그대로 적용됩니다.
Network Policy / Audit Logging 네트워크 정책 / 감사 기록
허용된 네트워크(예: 회사 사무실)에서만 접속하게 막는 것(Network Policy)과, 누가 언제 무엇을 조회했는지 기록을 남기는 것(Audit Logging). 둘 다 Snowflake 기능이 그대로 적용됩니다.
TARGET_LAG 목표 지연
"원본 데이터가 바뀌면 검색 결과에 최대 이만큼 늦게 반영되어도 된다"는 설정. '1 hour'로 두면 한 시간 안에 새 데이터가 검색됩니다. 짧을수록 최신이지만 갱신 비용이 늘어납니다. 10장에서 자세히.

9 System Architecture — 전체 구조

TL;DR

Cortex Search는 데이터 원본 → 인덱싱 → 검색 서빙 → API → 응용 프로그램의 다섯 층으로 이루어져 있습니다. 위에서 아래로 데이터가 흘러가며, 사용자는 맨 위(어떤 테이블을 검색할지)와 맨 아래(어떻게 결과를 쓸지)만 신경 쓰면 됩니다.

Cortex Search Service는 Snowflake 플랫폼의 세 계층(Storage 저장, Compute 계산, Services 서비스) 위에 구축된 서빙 인프라입니다. "아키텍처(Architecture)"는 건축 설계도처럼 시스템의 구성 요소와 연결 관계를 그린 것입니다.

공장 생산 라인을 떠올리면 됩니다. 원재료(Data Sources)가 들어오면 가공 라인(Indexing Pipeline)이 검색 가능한 형태(벡터 + 역색인)로 만들고, 창고(Serving Infrastructure)에 정리해 둡니다. 손님은 주문 창구(API Layer)를 통해 요청하고, 그 결과를 매장(Applications)에서 사용합니다.

각 층이 하는 일

  2. Indexing Pipeline (인덱싱 파이프라인)원본에서 SQL로 텍스트를 읽어 오고(Source Query), 바뀐 부분을 감지하고(Change Tracking), 임베딩 모델로 벡터를 만들고(Embedding Engine), 벡터 인덱스와 역색인을 구축합니다(Index Builder). Part I의 2~4장이 여기서 일어납니다.
  3. Serving Infrastructure (검색 서빙)실제 검색 요청을 처리하는 층. Vector Search, Keyword Search, Semantic Reranker가 여기서 돕니다. Part I의 3~6장.
  4. API Layer (접속 창구)외부에서 검색을 요청하는 세 가지 방법. REST API(웹 주소로 호출), Python SDK(파이썬 코드로 호출), SQL의 SEARCH_PREVIEW 함수(SQL 안에서 테스트). 16장에서 실제 코드를 봅니다.
  5. Applications (응용 프로그램)검색 결과를 실제로 쓰는 곳. RAG 챗봇, 사내 검색창, Cortex Agents의 도구, Marketplace의 Knowledge Extensions 등.

TL;DR

Cortex Search를 실제 운영할 때 중요한 네 가지 기능입니다. 자동 증분 갱신(데이터가 바뀌면 바뀐 부분만 다시 인덱싱), 필터(조건으로 결과 좁히기), 점수 조정(순위 규칙 바꾸기), 자동 중지(안 쓸 때 비용 절약).

10.1 Automatic Incremental Refresh — 자동 증분 갱신

원본 테이블에 새 상담 기록이 추가되거나 내용이 수정되면, Cortex Search는 바뀐 부분만 감지해서 인덱스를 갱신합니다. 전체를 다시 만들지 않기 때문에 빠르고 비용이 적습니다. "증분(Incremental)"은 "늘어난 만큼만"이라는 뜻입니다.

사전을 새로 찍을 때 매번 전체를 다시 조판하지 않고, 추가·수정된 단어 페이지만 바꿔 끼우는 것과 같습니다. TARGET_LAG는 "몇 시간마다 바뀐 페이지를 확인할지" 정하는 주기입니다.

10.3 Scoring Customization — 순위 규칙 조정

기본 설정으로도 잘 동작하지만, 서비스 특성에 따라 순위 규칙을 바꿀 수 있습니다. 예를 들어 뉴스 검색이라면 "최신 기사를 위로", 커뮤니티 검색이라면 "추천 많은 글을 위로" 올리고 싶을 것입니다. 이 설정들은 검색 요청 시 scoring_config라는 항목에 적습니다.

10.4 Auto-Suspend Serving — 안 쓸 때 자동 중지

검색 요청이 지정한 시간(최소 1,800초 = 30분) 동안 한 번도 없으면 서빙 컴퓨트가 자동으로 멈춥니다. 다음 검색 요청이 들어오면 자동으로 다시 켜지므로 사용자는 차이를 느끼지 못합니다(첫 요청만 약간 느릴 수 있음). 서빙 컴퓨트는 요청이 없어도 켜져 있으면 비용이 발생하기 때문에, 야간이나 주말에 쓰지 않는 서비스라면 큰 절감 효과가 있습니다.

12 Multi-Index Search — 컬럼별로 다른 검색 전략

TL;DR

기본 서비스는 컬럼 하나를 검색합니다. Multi-Index는 여러 컬럼에 각각 다른 종류의 인덱스(키워드용 / 벡터용 / 내가 가져온 벡터용)를 만들어, 컬럼마다 가장 알맞은 검색 방식을 적용하고 중요도도 따로 정할 수 있게 합니다. 2026년 3월 정식 출시(GA)된 기능입니다.

쇼핑몰 상품 검색을 생각해 보세요. 제품 코드(SKU)는 "AG1001"처럼 정확히 일치해야 하니 키워드 검색이 맞고, 상품 설명은 "가볍고 오래가는 노트북"처럼 뜻으로 찾아야 하니 의미 검색이 맞습니다. Multi-Index는 이렇게 컬럼마다 다른 검색기를 붙이고, "제품명 일치는 설명 일치보다 2배 중요"처럼 비중도 정할 수 있게 해 줍니다.

Use Case 1: RAG 챗봇

7장에서 원리를 설명한 RAG를 실제 서비스 구조로 그린 것입니다. 이번에는 "누가 누구에게 무엇을 보내는가"에 초점을 맞춰, 사용자 → 응용 프로그램 → Cortex Search → LLM → 사용자 순서로 따라가 봅니다. Application은 사용자가 보는 챗봇 화면 뒤에서 이 과정을 조율하는 프로그램입니다.

RAG Architecture with Cortex Search - Step-by-Step Flow
1
User → Application REQUEST
사용자가 자연어로 질문합니다.
"우리 회사 원격근무 정책에서 해외 근무가 가능한가요?"
2
Application → Cortex Search RETRIEVAL
Application이 Cortex Search Service에 검색 요청을 보냅니다. Hybrid Search(Vector + Keyword + Reranker)가 질문과 가장 관련 높은 문서 조각(chunks)을 Top-K개 반환합니다.
svc.search(query="해외 근무 정책", columns=["content"], limit=3)
Chunk 1: "원격근무 정책 v3.2: 해외 근무는 HR 승인 후 최대 90일까지 가능하며, 세금 관련 사전 확인이 필요합니다..."
Chunk 2: "2024년 원격근무 가이드: 장기 해외 근무 시 현지 법률 검토가 의무적이며, 보안 VPN 사용이 필수입니다..."
3
Application → Cortex LLM (AI_COMPLETE) AUGMENTATION + GENERATION
Application이 검색된 문서 chunks를 System Prompt에 Context로 삽입하고, 원래 사용자 질문과 함께 LLM에 전달합니다. LLM은 이 Context를 근거로 답변을 생성합니다.
[System] 아래 컨텍스트를 기반으로 정확하게 답변하세요.
[Context] {Chunk 1} {Chunk 2}
[User] 해외 근무가 가능한가요?
4
Cortex LLM → User GROUNDED RESPONSE
LLM이 Context에 근거하여 사실 기반(grounded) 답변을 생성합니다. 답변에는 출처(Source Citation)가 포함되어 사용자가 원본 문서를 확인할 수 있습니다.
"네, 해외 근무가 가능합니다. 원격근무 정책 v3.2에 따르면 HR 승인 후 최대 90일까지 해외 근무가 허용됩니다. 다만, 세금 관련 사전 확인과 현지 법률 검토가 필요하며, 보안 VPN 사용이 필수입니다."
Sources: 원격근무 정책 v3.2 2024년 원격근무 가이드

이 그림이 보여 주는 것: RAG는 4단계로 동작합니다. (1) 사용자가 질문하면, (2) Cortex Search가 지식 베이스에서 관련 문서를 검색(Retrieval)하고, (3) 검색된 문서를 LLM 프롬프트에 Context로 넣어(Augmentation) LLM이 답변을 생성(Generation)하며, (4) 근거 있는 답변과 출처를 사용자에게 돌려줍니다. 덕분에 환각을 줄이고 사내 최신 데이터 기반의 답을 낼 수 있습니다.

Use Case 2: Enterprise Search — 사내 검색

회사 인트라넷이나 고객 지원 시스템의 검색창 뒤에서 동작하는 검색 엔진으로 씁니다. 고객 지원 티켓, 기술 문서, 계약서 등을 대상으로 키워드 + 의미 기반 하이브리드 검색을 수행합니다. 이 경우 LLM 답변 생성 없이, 검색 결과 목록 자체를 사용자에게 보여 줍니다. "Fuzzy Matching"은 오타나 띄어쓰기 차이가 있어도 비슷한 것을 찾아 주는 것을 뜻합니다.

Use Case 3: Cortex Agents의 도구

Cortex Agent(14장)에 "문서 검색 도구"로 연결합니다. Agent가 사용자 질문을 보고 "이건 문서를 찾아봐야 답할 수 있겠다"고 판단하면 Cortex Search를 호출합니다. 단순 RAG뿐 아니라, 수천 건의 문서를 검색으로 좁힌 뒤 통계를 내는 Analytical Search에도 쓰입니다.

14 Cortex Agents Integration — AI 에이전트와 연결

TL;DR

Cortex Agent는 사용자의 질문을 이해하고, 필요한 도구(검색, SQL, AI 함수 등)를 스스로 골라 순서대로 실행해 답을 만드는 AI 비서입니다. Cortex Search는 Agent의 "문서 검색 도구"로 연결되며, Agent는 검색어를 스스로 만들고 결과를 읽어 답변을 구성합니다. 개발자는 설정 파일(YAML)만 쓰면 됩니다.

Agent 에이전트
LLM에 "도구를 골라 쓸 수 있는 능력"을 붙인 것. 질문을 받으면 계획을 세우고(어떤 도구를 어떤 순서로), 도구를 실행하고, 결과를 보고 다음 행동을 정합니다. 사람 비서가 자료실에 가고 계산기를 두드리는 것과 같습니다.
Tool 도구
Agent가 호출할 수 있는 기능 하나. Cortex Search(문서 검색), Cortex Analyst(자연어를 SQL로 바꿔 숫자 데이터 조회), 사용자 정의 함수 등. Agent에게 도구를 등록할 때는 "이 도구는 무엇을 할 수 있는지" 설명을 함께 적어 두어야 Agent가 언제 쓸지 판단할 수 있습니다.
YAML 야믈
설정 파일을 사람이 읽기 쉽게 적는 형식. 들여쓰기로 계층을 표현합니다. 16장의 Agent 설정 예시가 YAML입니다.

15 Cost Model — 비용은 어디서 발생하나

TL;DR

비용은 네 곳에서 발생합니다. 인덱스 만들 때 쓰는 Warehouse 계산, 임베딩 토큰, 검색 서빙 컴퍼트(켜져 있는 동안), 저장 공간. 가장 효과적인 절감 방법은 Primary Key 설정(증분 임베딩), Auto-Suspend(유휴 시 중지), 작은 Warehouse, 필요한 컬럼만 인덱싱입니다.

도서관을 운영하는 비용과 비슷합니다. 책을 분류하고 색인을 만드는 인건비(Warehouse Compute + Embedding Tokens), 도서관 문을 열어 두는 동안 드는 운영비(Serving Compute), 책과 색인 카드를 보관하는 공간 임대료(Storage). 운영비는 손님이 없어도 문이 열려 있으면 계속 나가므로, 손님이 없을 때 문을 닫는(Auto-Suspend) 것이 핵심 절감 포인트입니다.

Serving Compute (35%) - GB/mo indexed data
Embedding Tokens (30%) - Credits/M tokens
Warehouse Compute (25%) - Refresh credits
Storage (10%) - $/TB/month

위 비율(35/30/25/10%)은 항목 간 크기 감을 잡기 위한 예시이며, 실제 비율은 데이터 양, 갱신 빈도, 검색량에 따라 크게 달라집니다. 예를 들어 데이터가 거의 바뀌지 않고 검색만 많은 서비스라면 Serving Compute 비중이 훨씬 커집니다.

비용 절감 Best Practices:
  • Primary Key를 설정하여 증분 임베딩 활성화
  • AUTO_SUSPEND를 설정하여 유휴 서빙 비용 절감 (최소 1,800초)
  • 전용 Warehouse를 MEDIUM 이하로 설정
  • 소스 쿼리에서 필요한 컬럼만 SELECT하여 인덱스 크기 최소화
  • Multi-Index 쿼리 시 multi_index_query로 검색 대상 인덱스를 제한

TL;DR

16.1 서비스 생성 (SQL)

모든 것의 시작입니다. "이 테이블의 이 컬럼을 검색할 수 있게 만들어 줘"라는 SQL 한 문장입니다. 고객 상담 기록(support_transcripts) 테이블을 예로 듭니다.

-- 1. Cortex Search Service 생성
CREATE OR REPLACE CORTEX SEARCH SERVICE my_search_service
  ON transcript_text                        -- 검색 대상 컬럼
  ATTRIBUTES region                         -- 필터 가능 컬럼
  WAREHOUSE = my_wh                         -- Refresh용 Warehouse
  TARGET_LAG = '1 day'                      -- 소스 변경 반영 주기
  EMBEDDING_MODEL = 'snowflake-arctic-embed-l-v2.0'  -- 임베딩 모델
  AS (
    SELECT
        transcript_text,
        region,
        agent_id
    FROM support_transcripts
);
코드뜻
CREATE OR REPLACE CORTEX SEARCH SERVICE my_search_service"my_search_service"라는 이름의 검색 서비스를 만듭니다. 같은 이름이 이미 있으면 덮어씁니다(REPLACE).
ON transcript_text검색 대상 컬럼. 이 컬럼의 글이 임베딩되고 역색인됩니다. 사용자의 검색어는 이 컬럼과 비교됩니다.
ATTRIBUTES region필터(10.2)에 쓸 수 있는 컬럼. 검색 후 "region이 Asia인 것만" 같은 조건에 사용.
WAREHOUSE = my_wh인덱스를 만들고 갱신할 때 쓸 Warehouse(계산 자원). 비용 절감을 위해 MEDIUM 이하 권장(15장).
TARGET_LAG = '1 day'원본이 바뀌면 최대 하루 안에 검색에 반영. 더 빠른 반영이 필요하면 '1 hour' 등으로.
EMBEDDING_MODEL = 'snowflake-arctic-embed-l-v2.0'임베딩 모델 선택(11장). 한국어 상담 기록이므로 다국어 모델. 나중에 바꿀 수 없습니다.
AS ( SELECT transcript_text, region, agent_id FROM support_transcripts )어떤 데이터를 인덱싱할지 정하는 SQL(Source Query). 검색 컬럼, 필터 컬럼, 그리고 결과에 함께 돌려받고 싶은 컬럼(agent_id)만 골라 넣습니다. 필요 없는 컬럼을 빼면 저장 비용이 줄어듭니다.

16.2 검색 쿼리 (Python SDK)

파이썬 프로그램(예: 챗봇 서버)에서 검색하는 방법입니다. SDK 덕분에 API 주소나 인증 헤더를 직접 다루지 않고 함수 호출처럼 씁니다.

from snowflake.core import Root
from snowflake.snowpark import Session

session = Session.builder.configs(CONNECTION_PARAMS).create()
root = Root(session)

# 서비스 참조
svc = (root
  .databases["my_db"]
  .schemas["my_schema"]
  .cortex_search_services["my_search_service"]
)

# 검색 실행 (필터 + 제한)
resp = svc.search(
    query="인터넷 연결 문제",
    columns=["transcript_text", "region"],
    filter={"@eq": {"region": "Asia"}},
    limit=5
)
print(resp.to_json())
코드뜻

16.3 Multi-Index 서비스 생성

12장의 상품 카탈로그 예시를 SQL로 만든 것입니다. 16.1과 비교하면 ON 대신 컬럼별로 인덱스 종류를 지정하는 부분이 다릅니다.

-- Text Index + Vector Index 결합 (다국어 모델 사용)
CREATE OR REPLACE CORTEX SEARCH SERVICE product_search
  TEXT INDEXES (product_name, sku)
  VECTOR INDEXES (description MODEL='snowflake-arctic-embed-l-v2.0')
  WAREHOUSE = my_wh
  TARGET_LAG = '1 hour'
  AS (SELECT * FROM product_catalog);
코드뜻
TEXT INDEXES (product_name, sku)제품명과 제품 코드는 키워드 검색용 역색인으로. "AG1001" 같은 정확한 코드 검색에 강합니다.
VECTOR INDEXES (description MODEL='snowflake-arctic-embed-l-v2.0')상품 설명은 의미 검색용 벡터 인덱스로. 컬럼 옆에 어떤 임베딩 모델을 쓸지 지정합니다. 한국어 설명이면 다국어 모델을 씁니다.
TARGET_LAG = '1 hour'상품 정보는 자주 바뀌므로 한 시간마다 갱신 확인.
AS (SELECT * FROM product_catalog)테이블의 모든 컬럼(*)을 인덱싱 대상으로. 실제 운영에서는 필요한 컬럼만 고르는 것이 비용에 유리합니다.

코드뜻

16.6 Agent Tool 설정 (YAML)

14장의 Cortex Agent에 이 검색 서비스를 "도구"로 등록하는 설정입니다. Agent는 여기 적힌 설명(description)을 읽고 언제 이 도구를 쓸지 스스로 판단합니다. 그래서 설명을 사람에게 말하듯 구체적으로 적는 것이 중요합니다.

tools:
  - tool_spec:
      type: "cortex_search"
      name: "support_search"
      description: "고객 지원 티켓에서 관련 정보를 검색합니다"

tool_resources:
  support_search:
    search_service: "my_db.my_schema.my_search_service"
    max_results: "5"
    title_column: "title"
    id_column: "ticket_id"
    columns_and_descriptions:
      transcript_text:
        description: "고객 지원 대화 내용"
        type: "string"
        searchable: true
        filterable: false
      region:
        description: "지역. 유효 값: Asia, Europe, North America"
        type: "string"
        searchable: false
        filterable: true
코드뜻
tools: - tool_spec: type: "cortex_search"도구 목록에 Cortex Search 종류의 도구 하나를 추가합니다.
name: "support_search"이 도구의 이름. 아래 tool_resources에서 같은 이름으로 세부 설정을 연결합니다.
description: "고객 지원 티켓에서 관련 정보를 검색합니다"Agent에게 알려 주는 용도 설명. Agent는 질문이 고객 지원 관련이면 이 도구를 골라 씁니다.
search_service: "my_db.my_schema.my_search_service"실제로 연결할 검색 서비스의 전체 경로(데이터베이스.스키마.서비스).
max_results: "5"한 번에 최대 5건 검색.
title_column / id_columnAgent가 답변에 출처를 표시할 때 제목으로 쓸 컬럼(title)과 문서를 식별할 컬럼(ticket_id).
columns_and_descriptions: transcript_text: ... searchable: true, filterable: false각 컬럼이 무엇인지 설명하고, 검색어와 비교하는 컬럼인지(searchable), 필터로 쓸 컬럼인지(filterable) 알려 줍니다. 상담 내용은 검색 대상, 필터는 아님.
region: description: "지역. 유효 값: Asia, Europe, North America" ... filterable: trueregion은 필터용. 가능한 값을 설명에 적어 두면 Agent가 "아시아 고객 문제"라는 질문에서 스스로 region = Asia 필터를 만들어 냅니다.
